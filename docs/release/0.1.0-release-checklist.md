# `0.1.0` release checklist — alpha to stable and app migration

**Last updated:** 2026-10-31
**Current branch:** `release/0.1`
**Current state:** `0.1.0-alpha.1` published. `latest` is still
`0.1.0-alpha.0` (first-publish artifact). Trusted publishing is configured.
`ACTIVE_RELEASE=release/0.1` is set, so `main` cannot publish while this line
stabilizes.

This is the concrete continuation of the general runbooks:
[prerelease.md](prerelease.md), [stable.md](stable.md),
[hotfix.md](hotfix.md), and
[shenterm `consume.md`](https://github.com/shentechnologie/shenterm/blob/main/docs/release/consume.md).

> Counters continue across channels: `alpha.1` → `beta.2` → `rc.3` → `0.1.0`.
> Do not try to force `.0` for each stage.

Expected: `0.1.0-beta.2` (the counter continues from alpha).


Expected shape:

```text
alpha:  0.1.0-alpha.1
beta:   0.1.0-beta.2
latest: 0.1.0-alpha.0
```

`latest` deliberately stays on the first alpha until the stable release.

## 4. Ship stable `0.1.0`

```bash
bun changeset pre exit
git add .changeset/pre.json
git commit -m "chore: exit prerelease mode for 0.1.0"
git push
```

Before merging the stable Version Packages PR:

1. Confirm the PR version is exactly `0.1.0` for both packages.
2. Approve the CI run if it is `action_required`.
3. If the native module, podspec, gradle or vendored sources changed since the
   last proof, run the native proof first.

Merge the PR. The Release workflow publishes `0.1.0` to `latest`.

Verify:

```bash
npm dist-tag ls @literm/terminal-core
npm dist-tag ls @literm/react-native-terminal
npm view @literm/terminal-core@0.1.0 dist.attestations
```

Expected:

```text
alpha:  0.1.0-alpha.1
beta:   0.1.0-beta.2
rc:     0.1.0-rc.3
latest: 0.1.0
```

Both packages must have the same version.

## 5. Merge `release/0.1` back to `main`

Do this immediately after `0.1.0` is stable.

```bash
cd /Users/penguin/dev/literm
git checkout main
git pull --ff-only
git merge release/0.1
```

Resolve conflicts in `package.json` / `CHANGELOG.md` in favor of the released
`0.1.0` version. Keep unrelated `main` changes.

```bash
bun install
bun run release:verify
git push origin main
```

Then clear the GitHub repository variable:

- **Settings → Secrets and variables → Actions → Variables**
- Delete `ACTIVE_RELEASE`, or set it to the next active release branch.

The Release workflow on `main` runs and no-ops because `0.1.0` is already
published. If `main` has pending changesets for the next line, it may open a
Version Packages PR; leave it until you are ready to release that line.

Keep `release/0.1` for `0.1.x` patch support.

Optional cleanup:

```bash
git push origin --delete changeset-release/release/0.1
rm docs/release/first-alpha-0.1.0.md
```

The `changeset-release/release/0.1` branch may already be deleted after the
merge.

## Troubleshooting

| Symptom | What to do |
|---|---|
| Version Packages PR CI is `action_required` | Open the run and click **Approve and run**; the PR author is the bot |
| No Version PR appears | Check the Release run’s annotations; it should have found the changeset |
| Version PR targets `main` instead of `release/0.1` | Stop; do not merge; report it |
| `pre.json` formatting fails CI | Already ignored via `.prettierignore` |
| `latest` still points at an alpha | Expected until the stable `0.1.0` publish |
| Counter jumps to `beta.2` / `rc.3` | Expected; the counter is monotonic across channels |
| OIDC publish fails with 404 | Verify the trusted publisher and Node 24 in the workflow |
| OIDC publish fails with 403 | Re-check the trust fields and allowed `npm publish` action |
| Need to undo a release | See [rollback.md](rollback.md) |
